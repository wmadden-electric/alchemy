`Prisma.Compute` deploys an application onto Prisma's managed
runtime. One resource covers the whole path: optional build, artifact
upload, deployment, health check, and promotion — see
[Deployments](/prisma/compute/deployments) for the lifecycle.

## Framework apps

For frontend frameworks, prefer the [`Prisma.Website` family](/prisma/frontend/websites).
It provides framework-specific builds and native dev servers with the
same `rootDir`, `env`, `assets`, `dev`, and `domain` vocabulary as other
providers. Its output still runs on Bun in Compute, including static
sites. Use `Prisma.Compute` directly for custom builds, server apps,
and the Effect-native handlers below.

Point `path` at the app. With `build: "auto"`, alchemy detects the
framework, builds it, archives the output, and deploys the correct
server entrypoint:

```typescript
const app = yield* Prisma.Compute("api", {
  project,
  path: "./app",
  build: "auto",
  healthCheck: { path: "/api/health" },
  destroyOldDeployment: true,
});
```

The server must listen on `PORT` (injected at runtime). Auto-build
supports Bun, Next.js, Nuxt, Astro, TanStack Start, Vite, and NestJS. Generic
Vite projects are deployed as static SPAs. Use an
explicit build object when an app needs a custom command, output
directory, or entrypoint.

When `Prisma.Project` creates its default database, Prisma injects
system-managed `DATABASE_URL` and `DATABASE_URL_POOLED` values into
Compute deployments. Leave those keys out of `env`. For a standalone
`Prisma.Postgres` database, create a `Prisma.Connection` and pass its
outputs explicitly as shown in [Connections](/prisma/data/connections).

`app.url` is the deployed endpoint.

## Static sites

Generic Vite apps work with `build: "auto"`. To deploy a directory that already
contains static files, set `build.type` to `"static"` and point `outdir` at it.
Alchemy packages the files with the HTTP entrypoint Prisma Compute requires;
the application does not need its own server file or runtime dependency:

```typescript
const site = yield* Prisma.Compute("web", {
  project,
  path: "./site",
  build: {
    type: "static",
    outdir: ".",
  },
});
```

Add `command` when the output directory needs to be built first:

```typescript
const site = yield* Prisma.Compute("web", {
  project,
  path: "./app",
  build: {
    type: "static",
    command: "bun run build",
    outdir: "dist",
    spa: true,
  },
  dev: { command: "bun run dev", port: 5173 },
});
```

Set `spa: true` for client-side routers so unmatched paths serve
`index.html`. Leave it disabled for static sites that should return `404` for
missing files. Directory indexes redirect to a trailing-slash URL so relative
asset links resolve correctly.

For static builds, `archiveIgnore` patterns are relative to `outdir`. The
configured index page must remain in the archive; excluding it rejects the
deployment.

## Effect-native apps

Pass `main` and an Effect body instead of a build, and the app is
bundled from your Stack file — same shape as an Effect-native
Cloudflare Worker or Lambda:

```typescript
export default Prisma.Compute(
  "api",
  { project, main: import.meta.filename },
  Effect.gen(function* () {
    const db = yield* Prisma.Connect(connection);
    const sql = yield* SQL.Postgres({ url: db.databaseUrl });

    return {
      fetch: Effect.gen(function* () {
        const users = yield* sql`SELECT * FROM users`;
        return yield* HttpServerResponse.json(users);
      }),
    };
  }).pipe(Effect.provide(Prisma.ConnectBinding)),
);
```

## Custom domains

Creating the resource starts DNS and certificate
provisioning; use `domain.dnsRecords` to configure DNS and inspect
`domain.status` before directing production traffic:

```typescript
const domain = yield* Prisma.CustomDomain("api-domain", {
  app,
  hostname: "api.example.com",
});
```

Prisma also asks the workspace to prove it owns the hostname with a
`TXT` record. `Prisma.DomainOwnership` publishes the record through your DNS
host and proves it; pass it to the domain so the domain is created after
the proof:

```typescript
const ownership = yield* Prisma.DomainOwnership("api-ownership", {
  project,
  domain: "api.example.com",
  dns: Cloudflare.DNS.Adapter(),
});
const domain = yield* Prisma.CustomDomain("api-domain", {
  app,
  hostname: "api.example.com",
  ownership,
});
```

To serve many apps under one domain, prove a wildcard once and attach each
hostname to it:

```typescript
const ownership = yield* Prisma.DomainOwnership("example.com", {
  project,
  domain: "*.example.com",
  dns: Cloudflare.DNS.Adapter(),
});
yield* Prisma.CustomDomain("api", { app: api, hostname: "api.example.com", ownership });
yield* Prisma.CustomDomain("admin", { app: admin, hostname: "admin.example.com", ownership });
```

A wildcard and its apex share one record name
(`_prisma-verification.example.com`), so prove only one of them per zone.
Without `dns`, publish the record yourself: the deploy fails with
`PrismaDomainOwnershipRequired`, which names the record.

A deploy succeeds only once Prisma reports the ownership `verified`. The ownership's `status` and `expiresAt` are what Prisma reported when the deploy last proved the domain; an unchanged redeploy does not check again.

Changing the hostname or app in place is intentionally rejected.
Create a second domain, verify DNS and TLS, cut traffic over, and then
remove the old resource.

## Routing URLs

`Prisma.RoutingUrl` saves a hostname for an app before its DNS exists. The deploy succeeds at once, and the resource reports the records still to publish:

```typescript
const url = yield* Prisma.RoutingUrl("api", {
  app,
  hostname: "api.example.com",
});
// url.status: "pending"
// url.records: the TXT record that proves ownership and the CNAME to the switchboard
// url.setupUrl: the Console page that shows what to do next
```

Prisma makes the RoutingUrl `active` once both records are published. It also creates the domain ownership the `TXT` record proves; destroying the RoutingUrl leaves that domain ownership in place.

A RoutingUrl is identified on its Branch by `logicalId`, which defaults to the resource's name. A RoutingUrl Prisma already made for the same app and hostname, with no `logicalId`, is taken over. Changing the hostname of an `active` RoutingUrl fails before anything changes, until the new hostname has a verified domain ownership and its `CNAME`.

Changing the hostname to an apex domain such as `example.com` is refused, because Prisma needs a direct `CNAME`, which an apex cannot have. The check does not see a RoutingUrl in another workspace that holds the new hostname; then the change goes through, and the new hostname stays `pending` with `heldBy` set.

To replace a `Prisma.CustomDomain` with a `Prisma.RoutingUrl` for the same hostname, keep the CustomDomain with `RemovalPolicy.retain()`, or remove it in an earlier deploy. The RoutingUrl takes over the row the CustomDomain made, and the CustomDomain's delete would remove that row.

Don't declare a `Prisma.DomainOwnership` for the same exact hostname as a `Prisma.RoutingUrl`. The `Prisma.DomainOwnership` takes over the domain ownership Prisma created for the RoutingUrl, and deletes it on destroy.

## Local dev

Under `alchemy dev`, `dev.command` runs your app locally (e.g.
`vite dev`) with the same env the deployed app would see — including
connection bindings, which resolve to the local
[dev database](/prisma/data/postgres#local-dev):

```typescript
const app = yield* Prisma.Compute("web", {
  project,
  path: ".",
  dev: { command: "bun run dev" },
  env: { DATABASE_URL: connection.databaseUrl },
});
```
